# Automatic Work Log via Claude Code Stop Hook

## What this does

A Claude Code `Stop` hook that automatically logs a 2-3 sentence summary of each conversation turn to a daily markdown file (`~/.work-log/YYYY-MM-DD.md`). The summary is generated by a background Haiku subprocess — no re-entry into the main session, no context pollution, cheaper than using the main model.

Each entry looks like:

```
## 14:10 - my-project (feature/my-branch)
Completed i_nuvigator migration for flutter_http: added dependency, updated
LogoutInterceptor to use IRouter, and fixed redirect_interceptor_test setup.
Key finding: interceptor correctly dispatches the logout deeplink on 403.
Next: validate all tests pass and prepare PR.
```

## How it works

The Claude Code `Stop` event fires after every assistant turn and delivers a JSON payload on stdin:

```json
{
  "session_id": "...",
  "transcript_path": "/path/to/session.jsonl",
  "cwd": "/path/to/project",
  "hook_event_name": "Stop",
  "stop_hook_active": false,
  "last_assistant_message": "Full text of what Claude just said..."
}
```

The hook reads `last_assistant_message` (the current turn's response) plus git context, then spawns `claude -p --model claude-haiku-4-5-20251001` in the background to write a concise summary.

## Setup

### Recommended: use `somnio hooks`

```bash
somnio hooks
```

This copies the script to `~/.claude/hooks/work-log-stop.sh`, makes it executable, and merges the Stop hook entry into `~/.claude/settings.json` — all in one step, idempotently. Run it again after any CLI update to pick up script changes.

### Manual setup

If you prefer to install by hand:

#### 1. Create the hook script

Save this to `~/.claude/hooks/work-log-stop.sh` and make it executable:

```bash
#!/usr/bin/env bash
set -euo pipefail

# Recursion guard: prevent the Haiku subprocess from triggering this hook again
[ -n "${WORK_LOG_CHILD:-}" ] && exit 0

DATE=$(date '+%Y-%m-%d')
LOG=~/.work-log/$DATE.md
mkdir -p ~/.work-log

# Debounce: skip if the log was written less than 5 seconds ago
# (prevents duplicate entries when multiple sessions stop simultaneously)
# python3 is used for mtime because stat flags differ between macOS (-f %m) and Linux (-c %Y).
LAST=$(python3 -c "import os,sys; print(int(os.path.getmtime(sys.argv[1])))" "$LOG" 2>/dev/null || echo 0)
AGE=$(( $(date +%s) - LAST ))
[ "$AGE" -lt 5 ] && exit 0

STDIN=$(cat)

CWD=$(echo "$STDIN" | python3 -c 'import json,sys; d=json.load(sys.stdin); print(d.get("cwd",""))' 2>/dev/null || true)
[ -z "$CWD" ] && CWD=$(pwd)

BRANCH=$(cd "$CWD" && git rev-parse --abbrev-ref HEAD 2>/dev/null || echo 'no-git')

# Log root repo + worktree so Clockify mapping works at the repo level.
GIT_COMMON=$(cd "$CWD" && git rev-parse --git-common-dir 2>/dev/null || echo "")
if [ -n "$GIT_COMMON" ]; then
  # git rev-parse --git-common-dir returns a relative path (.git) for main checkouts.
  # Resolve to absolute before dirname/basename so ROOT_REPO is correct in both cases.
  case "$GIT_COMMON" in /*) ;; *) GIT_COMMON="$CWD/$GIT_COMMON" ;; esac
  ROOT_REPO=$(basename "$(dirname "$GIT_COMMON")")
  WORKTREE=$(basename "$CWD")
  if [ "$ROOT_REPO" = "$WORKTREE" ]; then
    PROJ="$ROOT_REPO"
  else
    PROJ="$ROOT_REPO/$WORKTREE"
  fi
else
  PROJ=$(basename "$CWD")
fi

LAST_MSG=$(echo "$STDIN" | python3 -c 'import json,sys; d=json.load(sys.stdin); print(d.get("last_assistant_message","")[:3000])' 2>/dev/null || true)

printf "\n## %s - %s (%s)\n" "$(date '+%H:%M')" "$PROJ" "$BRANCH" >> "$LOG"

if [ "${#LAST_MSG}" -lt 20 ]; then
  printf "No significant output.\n" >> "$LOG"
  exit 0
fi

GIT_STAT=$(cd "$CWD" && { git log --oneline -3 2>/dev/null; echo "---"; git diff --stat HEAD 2>/dev/null | head -5; } || true)

PROMPT=$(printf 'Write 2-3 sentences for a work log entry. Be specific: name files, functions, root causes, decisions. Cover: what was accomplished, the key technical finding, and any open question or next step. Output ONLY the sentences.\n\nProject: %s (%s)\nRecent git:\n%s\n\nFinal response:\n%s' \
  "$PROJ" "$BRANCH" "$GIT_STAT" "$LAST_MSG")

CLAUDE_BIN=$(which claude 2>/dev/null || echo "claude")

(
  WORK_LOG_CHILD=1 "$CLAUDE_BIN" -p \
    --model claude-haiku-4-5-20251001 \
    --no-session-persistence \
    "$PROMPT" >> "$LOG" 2>/dev/null \
  || printf "(summary unavailable)\n" >> "$LOG"
) &

exit 0
```

```bash
chmod +x ~/.claude/hooks/work-log-stop.sh
```

#### 2. Register the hook in `~/.claude/settings.json`

```json
{
  "hooks": {
    "Stop": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "~/.claude/hooks/work-log-stop.sh"
          }
        ]
      }
    ]
  }
}
```

## Design decisions

### Why a subprocess instead of `asyncRewake`

The built-in `asyncRewake: true` mechanism re-enters the **main session** to write the log entry. This has two problems:

1. **Context pollution** — the rewake message and tool call are added to the session's context window, consuming tokens on every turn.
2. **Cost** — it uses the same model as the main session (e.g. Sonnet 1M context) just to write a log line.

The subprocess approach is isolated: a separate `claude -p` process with its own context, using Haiku instead of the main model.

### Why Haiku

The summary task (restate what was just said in 2-3 specific sentences) is well within Haiku's capability. Using `claude-haiku-4-5-20251001` is significantly cheaper than Sonnet for this kind of writing task.

### Why `last_assistant_message` instead of JSONL parsing

The Stop hook payload includes `last_assistant_message` — the full text of the current turn's response. This is already the richest single signal: it's what Claude just said, and for technical sessions it contains all the detail needed for a good log entry.

Parsing the JSONL transcript would add complexity and, for long-running sessions (days of conversation), would include stale context from unrelated earlier turns.

### Recursion guard

`WORK_LOG_CHILD=1` is set as an environment variable when spawning the Haiku subprocess. The subprocess's `claude -p` session also triggers the Stop hook when it finishes. The guard at the top of the script detects this variable and exits immediately, preventing an infinite loop.

### 5-second debounce

When multiple Claude sessions are running simultaneously and stop within the same second, they can race to write to the log. The debounce skips the hook if the log was written less than 5 seconds ago, which prevents duplicate entries for rapid back-and-forth while still allowing concurrent sessions to log within a few seconds of each other.

`python3` is used to read the file mtime instead of `stat` because `stat` flag syntax differs between macOS (`-f %m`) and Linux (`-c %Y`). `python3 os.path.getmtime` works on both.

## Log format

Entries are appended to `~/.work-log/YYYY-MM-DD.md` (one file per day):

```markdown
## HH:MM - project-name (git-branch)
2-3 sentence summary of what was accomplished this turn.
```

The `project-name` field depends on whether you are in a main checkout or a git worktree:

| Context | Example header |
|---------|----------------|
| Main checkout | `## 09:15 - somnio-ai-tools (main)` |
| Git worktree | `## 14:10 - mini-meta-repo/refactor-flutter_http (feat/my-branch)` |

For worktrees the format is `root-repo/worktree-directory`. The `clockify-tracker` skill splits on `/` to extract the root repo name, so any number of worktrees from the same repo map to the same Clockify project automatically.

Multiple sessions and projects interleave chronologically in the same daily file.

## Relation to Clockify

At the end of the day (or week), run:

```
/clockify-tracker use logs for this week
```

The [`clockify-tracker`](../commands/clockify-tracker.md) skill reads your `~/.work-log/` files, maps each repo to a Clockify project (asked once, saved to `~/.clockify-prefs.json`), generates a 2-sentence executive summary per entry, and shows a full preview before posting. Each log entry's timestamp maps directly to a Clockify time entry — no manual input required beyond confirming the preview.
