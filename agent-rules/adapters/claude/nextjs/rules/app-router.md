# Next.js App Router

How to structure routes, layouts and request-time boundaries in a Next.js App Router project, and how to find the documentation that matches the installed Next.js version.

## Patterns

### Check the installed version and its bundled docs first

Before writing or reviewing Next.js code, read the installed version (`node_modules/next/package.json` or the lockfile) and use the documentation that matches it.

- **Next.js 16.2+** ships version-matched docs at `node_modules/next/dist/docs/` (same structure as nextjs.org/docs).
- **Next.js 16.3+**: when `next dev` detects a coding agent it creates or updates a managed block in `AGENTS.md` (between `<!-- BEGIN:nextjs-agent-rules -->` and `<!-- END:nextjs-agent-rules -->`) pointing agents to those docs. Commit that block with your work; do not delete it. It can be configured or disabled with the `agentRules` option in `next.config`.
- **Next.js 16.1 and earlier**: no bundled docs. Run `npx @next/codemod@canary agents-md` to download a version-matched copy to `.next-docs/` and index it in `AGENTS.md`.
- Every page on nextjs.org/docs is also available as Markdown (append `.md`), with an index at `https://nextjs.org/docs/llms.txt`.
- Official workflow Skills (cache components adoption, dev loop, bundle optimizer) install with `npx skills add vercel/next.js` (or `--skill <name>` for one).

```bash
node -p "require('next/package.json').version"
ls node_modules/next/dist/docs/01-app/03-api-reference   # 16.2+
ls .next-docs                                            # projects that ran the agents-md codemod
```

### Async `params` and `searchParams`

Since Next.js 15, `params` and `searchParams` passed to pages, layouts, route handlers and `generateMetadata` are Promises. Await them (Server Components) or unwrap with React `use()` (Client Components). Prefer the generated global helpers `PageProps<'/route'>`, `LayoutProps<'/route'>` and `RouteContext<'/route'>` (types generated by `next dev`, `next build` or `next typegen`).

```tsx
// app/blog/[slug]/page.tsx
export default async function Page(props: PageProps<'/blog/[slug]'>) {
  const { slug } = await props.params
  const { page = '1' } = await props.searchParams
  const post = await getPost(slug)
  return <Article post={post} page={Number(page)} />
}
```

### Push request-time reads down the tree

Awaiting `params`, `cookies()` or `headers()` at the top of a layout makes the whole segment wait. Await them in the smallest component that needs them, behind `<Suspense>`, so the rest of the route can prerender and stream.

```tsx
// app/shop/[slug]/layout.tsx
import { Suspense } from 'react'

export default function Layout({ children, params }: LayoutProps<'/shop/[slug]'>) {
  return (
    <div>
      <Sidebar />
      <Suspense fallback={<h1>Loading…</h1>}>
        {params.then(({ slug }) => <SlugHeading slug={slug} />)}
      </Suspense>
      {children}
    </div>
  )
}
```

### Use the special files for UI states

Each segment can define `loading.tsx` (Suspense fallback), `error.tsx` (must be a Client Component), `not-found.tsx`, and at the root `global-error.tsx`. Call `notFound()` from `next/navigation` when a resource does not exist instead of rendering an empty page.

```tsx
// app/products/[id]/page.tsx
import { notFound } from 'next/navigation'

export default async function Page(props: PageProps<'/products/[id]'>) {
  const { id } = await props.params
  const product = await getProduct(id)
  if (!product) notFound()
  return <ProductView product={product} />
}
```

```tsx
// app/products/[id]/error.tsx
'use client'

export default function Error({ error, reset }: { error: Error & { digest?: string }; reset: () => void }) {
  return (
    <div role="alert">
      <p>Something went wrong.</p>
      <button onClick={() => reset()}>Try again</button>
    </div>
  )
}
```

### Route groups, private folders and colocation

- `(group)` folders organize routes and share layouts without affecting the URL.
- `_folder` private folders are excluded from routing; use them for colocated components and helpers.
- Only `page` and `route` files are publicly routable; a segment cannot contain both `page.tsx` and `route.ts`.
- Keep shared non-route code outside `app/` (for example `src/lib`, `src/components`, `src/data`).

```text
app/
  (marketing)/
    layout.tsx
    page.tsx
  (dashboard)/
    layout.tsx
    settings/
      page.tsx
      _components/
        settings-form.tsx
  api/
    webhooks/
      route.ts
```

### Proxy (formerly Middleware)

In Next.js 16 the `middleware` file convention is deprecated and renamed to `proxy` (`proxy.ts` at the project root or in `src/`, exporting `proxy` or a default function). Proxy defaults to the Node.js runtime and setting `runtime` in it throws. On 15.x and earlier the file is `middleware.ts` exporting `middleware`. Migrate with `npx @next/codemod@canary middleware-to-proxy .`.

Use proxy for redirects, rewrites, headers and optimistic (cookie-only) checks. Always scope it with a `matcher`, and never rely on it as the only authorization layer (see `security.md`).

```ts
// proxy.ts (Next.js 16+)
import { NextResponse, type NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  if (request.nextUrl.pathname === '/old-pricing') {
    return NextResponse.redirect(new URL('/pricing', request.url))
  }
  return NextResponse.next()
}

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)'],
}
```

### Pages Router coexistence

`pages/` and `app/` can coexist during migration, but a given URL must be served by only one of them. Do not add new features to `pages/` in an App Router project; Pages Router APIs (`getServerSideProps`, `getStaticProps`, `next/router`) do not work in `app/`, and App Router APIs (`next/navigation`, Server Components, Server Actions) do not work in `pages/`.

## Rules

- Read the installed Next.js version and its bundled docs (`node_modules/next/dist/docs/` on 16.2+, `.next-docs/` via the `agents-md` codemod on older versions) before writing framework code.
- Keep the managed `AGENTS.md` block that `next dev` writes on 16.3+ committed.
- Type pages and handlers with `PageProps`, `LayoutProps` and `RouteContext`; run `next typegen` in CI if types are not generated by the build.
- Await `params`/`searchParams` as close as possible to where they are used, behind `<Suspense>`.
- Call `notFound()`, `redirect()` and `permanentRedirect()` from `next/navigation` instead of hand-rolled responses in pages.
- Give every route segment that fetches data a `loading.tsx` or an explicit `<Suspense>` boundary, and an `error.tsx` where failure is plausible.
- Scope `proxy.ts`/`middleware.ts` with a `matcher` that excludes `_next/static`, `_next/image` and public assets.

- Avoid treating `params` or `searchParams` as synchronous objects on Next.js 15+.
- Avoid creating `middleware.ts` in a Next.js 16 project instead of `proxy.ts`, or `proxy.ts` in a 15.x project where it is not recognized.
- Avoid setting `export const runtime` inside `proxy.ts`.
- Avoid writing `error.tsx` without `'use client'`.
- Avoid returning `null` from a page for a missing resource instead of calling `notFound()`.
- Avoid putting both `page.tsx` and `route.ts` in the same segment.
- Avoid importing `next/router` in App Router code (use `next/navigation`).
- Avoid deleting the `nextjs-agent-rules` block from `AGENTS.md`; `next dev` re-creates it.
