# Next.js Best Practices Format Enforcer

> Enforce Markdown report format for all analysis outputs. Ensures consistent, readable reports suitable for documentation.

---

## FORMAT REQUIREMENTS

**CRITICAL**: All analysis outputs MUST follow these rules:

1.  **USE MARKDOWN FORMATTING**:
    *   `#` for main title, `##` for sections, `###` for subsections
    *   `**bold**` for field labels and key terms. Bold the field label only; never bold the numeric value after `**Score:**`.
    *   Backticks for file paths and code references
    *   `- ` for bullet points

2.  **MARKDOWN STRUCTURE**:
    *   Section headers: `## N. Section Name`
    *   Sub-headers: `### Key Findings`, `### Violations`, `### Recommendations`
    *   Code refs: `` `generateMetadata` ``
    *   File paths: `` `app/(shop)/products/[id]/page.tsx:42` ``

3.  **SECTION STRUCTURE**:
    Each scored section must include, in this order:
    - `**Score:**` (0-100 integer with label, or `N/A` with the reason)
    - `**Description:**` (one-paragraph summary)
    - The section's structured sub-fields from `assets/report-template.md`
    - `### Key Findings` (3-7 bullet points)
    - `### Violations` (file paths with line numbers)
    - `### Recommendations` (prioritized actions)

4.  **SCORING LABELS**:
    - Strong: 85-100
    - Fair: 70-84
    - Weak: 0-69

5.  **FILE REFERENCES FORMAT**:
    - Always use: `path/to/file.tsx:line_number`
    - Example: `app/actions/posts.ts:18` — Server Action writes without an authorization check

6.  **VERSION STATEMENTS**:
    - The Executive Summary states the installed Next.js version and the docs
      source used. A finding that depends on a version-specific API or default
      names that version; if the version is Unknown, the finding says
      "unverified against the installed version".

7.  **CLOSING APPENDIX**:
    - The report MUST close with an unnumbered `## Appendix: Scoring Methodology` block, placed
      between the Evidence Index section and `## Report Metadata`.
    - Its `| Section | Weight |` rows MUST match this skill's own Score Breakdown rows and MUST
      sum to 100%.
    - Weights appear ONLY in that appendix and in `references/best-practices-generator.md` —
      they must NEVER appear as a column in the `## 2. Score Breakdown` table.

8.  **REPORT METADATA**:
    - The last block is `## Report Metadata`, a `| Field | Value |` table copied from the
      template with the `Generated by` row unchanged.

## EXAMPLE OUTPUT FORMAT

```markdown
## 6. Server Actions & Route Handlers

**Score:** 62/100 (Weak)

**Description:**
Twelve Server Actions and four Route Handlers. Inputs are validated with zod in most actions, but three mutating actions rely on the page-level session check only.

**Inventory:**
- Server Actions: 12 in 5 files
- Route Handlers: 4 (`GET` x3, `POST` x1)

### Key Findings
- 9/12 actions parse input with zod before use
- 3/12 mutating actions have no in-action authorization check
- Mutations revalidate with tags where tags exist

### Violations
- `app/actions/posts.ts:18` — [Authz Issue]: `deletePost` writes without re-checking the session (Critical)
- `app/api/export/route.ts:7` — [Validation Issue]: `searchParams` used in a query unvalidated (High)

### Recommendations
1. Move authorization into a `server-only` data access layer and call it from every action
2. Validate `searchParams` with a zod schema before the query
```

---

ENFORCE THIS MARKDOWN FORMAT FOR ALL ANALYSIS OUTPUTS.
