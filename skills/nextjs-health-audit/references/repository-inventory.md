# Next.js Repository Inventory

> Detect repository structure, router model (App Router / Pages Router / mixed), routing conventions, special files, output mode, bundler, monorepo setup and deployment target hints for Next.js projects.

---

Goal: Inventory how the Next.js application is structured and routed,
and validate the architecture patterns that keep it maintainable.

EFFICIENCY REQUIREMENTS:
- Target: ≤ 6 total tool calls for this entire analysis
- Use batch find/ls commands to inventory directory structure in one pass
- Read multiple package.json / config files per tool call using parallel reads
- Do NOT read individual source files to count them — use find + wc
- Exclude `node_modules`, `.next`, `out`, `dist`, `build`, `coverage`
  from every `find`

REPOSITORY STRUCTURE DETECTION:

1. **Next.js Apps and Monorepo**:
   - Locate every `package.json` that depends on `next` — each is a
     Next.js app (monorepos often have several under `apps/`)
   - Monorepo signals: `pnpm-workspace.yaml`, `"workspaces"` in root
     `package.json`, `turbo.json`, `nx.json`, `lerna.json`
   - Shared packages consumed by the apps (`packages/ui`,
     `packages/config`, ...) and whether the app lists them in
     `transpilePackages`
   - If monorepo: analyze each Next.js app; report cross-app consistency
   - Don't penalize the monorepo structure itself

2. **Router Model** (per app):
   - App Router: an `app/` directory (or `src/app/`) containing
     `layout.*` and `page.*` files
   - Pages Router: a `pages/` directory (or `src/pages/`) containing
     page files, `_app.*`, `_document.*`, `pages/api/*`
   - **Mixed**: both present — record which routes still live in
     `pages/` (incremental migration in progress, or forgotten routes)
   - Count routes:
     ```bash
     find app src/app -name 'page.*' -not -path '*/node_modules/*' 2>/dev/null | wc -l
     find app src/app -name 'route.*' -not -path '*/node_modules/*' 2>/dev/null | wc -l
     find pages src/pages -type f \( -name '*.tsx' -o -name '*.ts' -o -name '*.jsx' -o -name '*.js' \) 2>/dev/null | wc -l
     ```

3. **`src/` layout**: whether `app/`/`pages/` live at the root or under
   `src/` (both valid; inconsistency across apps in a monorepo is a finding)

4. **App Router conventions** (count and list examples):
   - Route groups: directories named `(group)`
   - Dynamic segments: `[param]`, catch-all `[...slug]`, optional
     catch-all `[[...slug]]`
   - Parallel routes: slots named `@slot` (and their `default.*` files)
   - Intercepting routes: directories starting with `(.)`, `(..)`,
     `(..)(..)` or `(...)`
   - Private folders: `_folder`
   - Special files per segment: `layout`, `template`, `loading`, `error`,
     `global-error`, `not-found`, `default`, `route` (Route Handlers)
   - Metadata files: `sitemap.*`, `robots.*`, `opengraph-image.*`,
     `icon.*`, `manifest.*`
   - Flag: segments with data fetching but no `loading.*` or `<Suspense>`
     boundary nearby are reported by the State Management step; here only
     count `loading.*` and `error.*` coverage (segments with a page vs
     segments with an error boundary)

5. **Root-level special files**:
   - `proxy.ts|js` (current convention) or `middleware.ts|js` (deprecated
     name since Next.js 16 — renamed to `proxy`; codemod:
     `npx @next/codemod@canary middleware-to-proxy .`). Record which one
     exists, its `config.matcher`, and whether it does authentication
     (authorization must ALSO be checked inside each Route Handler and
     Server Action — Proxy alone is not a security boundary)
   - `instrumentation.ts|js` (server observability: OpenTelemetry,
     Sentry, ...) and `instrumentation-client.ts|js`
   - `next-env.d.ts` (generated by Next.js; flag manual edits to it)

6. **Output mode and deploy target hints**:
   - `output` in `next.config.*`: `'standalone'` (self-host / Docker),
     `'export'` (static export — no server features: no Route Handlers
     with dynamic behavior, no Proxy, no Server Actions, no ISR), or
     default (server)
   - `vercel.json` (Vercel), `Dockerfile` / `docker-compose.yml`
     (self-host; check it copies `.next/standalone` when `output:
     'standalone'`), `netlify.toml`, `amplify.yml`, `fly.toml`,
     `render.yaml`, `open-next.config.ts` (OpenNext / AWS / Cloudflare),
     `wrangler.toml`
   - `adapterPath` in `next.config.*` (custom deployment adapter)

7. **Bundler**:
   - Turbopack vs webpack: inspect `package.json` scripts for
     `next dev --turbopack` / `--turbo`, `next build --turbopack`, or
     `--webpack`; a `webpack` function or `turbopack` key in
     `next.config.*`. Recent Next.js majors use Turbopack by default for
     both dev and build — read the installed version before stating it,
     and record "custom webpack config present" as a migration risk when
     it exists alongside Turbopack

FOLDER ORGANIZATION ANALYSIS:

8. **Feature / colocation organization**:
   - Colocated route-private components (`app/(group)/dashboard/_components/`)
     vs a global `components/` dump
   - Feature folders: `src/features/`, `src/modules/`
   - Shared layers: `lib/`, `utils/`, `hooks/`, `types/`, `services/`,
     `server/` (server-only code), `actions/` (Server Actions)
   - Server/client separation: count files importing `server-only` /
     `client-only`

9. **Directory Inventory**:
   - List top-level directories of the app (and `src/`)
   - Count: components, hooks, route segments, Route Handlers, Server
     Action files (files whose first statement is `'use server'`), Client
     Component files (first statement `'use client'`)
     ```bash
     grep -rlE "^['\"]use client['\"]" --include='*.tsx' --include='*.ts' --include='*.jsx' --include='*.js' app src components 2>/dev/null | wc -l
     grep -rlE "^['\"]use server['\"]" --include='*.ts' --include='*.tsx' --include='*.js' app src 2>/dev/null | wc -l
     ```

COMPONENT FILE SIZE ANALYSIS:

10. **Component File Size**:
    For all `*.tsx`/`*.jsx` files in the app source:
    - Files < 150 lines: Healthy
    - Files 150-300 lines: Acceptable
    - Files > 300 lines: FLAG for review
    - Files > 500 lines: CRITICAL FLAG
    Treat `page.*` and `layout.*` over 300 lines as a stronger signal:
    route files should compose, not implement.

NAMING CONVENTIONS:

11. **Naming Check**:
    - Next.js special files are lowercase by convention (`page.tsx`,
      `layout.tsx`, `route.ts`) — never flag them
    - Component files: PascalCase (`UserProfile.tsx`) or kebab-case
      (`user-profile.tsx`) — either is fine; flag inconsistency
    - Flag `.js`/`.jsx` source in a TypeScript project

OUTPUT FORMAT:

Provide structured analysis:
- Next.js apps found: [list of paths] (monorepo tool: [pnpm workspaces/Turborepo/Nx/none])
- Router model: [App Router/Pages Router/Mixed] (per app)
- `src/` layout: [Yes/No]
- Routes: [N] pages, [N] Route Handlers, [N] Pages Router files, [N] API routes
- Route groups / parallel routes / intercepting routes / dynamic segments: [counts]
- `loading.*` / `error.*` / `not-found.*` coverage: [counts vs page segments]
- Proxy / middleware: [proxy.ts / middleware.ts (deprecated name) / none], matcher: [value]
- Instrumentation: [instrumentation.ts / instrumentation-client.ts / none]
- Output mode: [default/standalone/export]
- Bundler: [Turbopack/webpack/custom webpack config]
- Deploy target hints: [vercel.json / Dockerfile / OpenNext / ... / none found]
- `'use client'` files: [N] / `'use server'` files: [N] / total component files: [N]
- Organization pattern: [Colocated/Feature-based/Component-based/Flat/Mixed]
- Component file size analysis:
  * Files < 150 lines: [Count]
  * Files 150-300 lines: [Count]
  * Files > 300 lines: [Count] (flag for review)
  * Files > 500 lines: [Count] (critical - list files)

- Risks identified
- Recommendations

SCORING GUIDANCE (Architecture section):

Strong (85-100):
- One router model (or a documented, progressing migration)
- Route files compose; logic colocated or in feature/server layers
- `loading`/`error` boundaries where data is fetched
- Server-only code separated (`server-only`, `server/` layer)
- `proxy.ts` (not the deprecated `middleware.ts`) with a precise matcher, if used

Fair (70-84):
- Mixed router without a clear migration path, or partial boundary coverage
- Some large route/component files
- Minor naming inconsistencies

Weak (0-69):
- Flat structure with logic in `page.*`/`layout.*` files
- Multiple oversized files, no error/loading boundaries
- Authorization enforced only in Proxy/middleware
