# Module Map

> Detect the stack and workspace layout, inventory the source files with the
> fixed metrics script, and classify every module into one role of the
> architecture standard. The map this step writes is the input every later
> step measures against.

---

Goal: Produce `data/files.tsv`, `data/inventory.json`, `data/module_map.tsv`
and a module-map artifact that say, with evidence, which modules the
codebase has, what role each plays, whether its boundary is physical, and
which drivers apply.

STANDARD:
- Read `architecture-standard.md`, in the same directory as this file,
  before classifying anything. Sections 1 (terms), 2 (profile and
  drivers) and 3 (roles) apply here.

READ-ONLY DISCIPLINE:
- Never modify the audited repository. Use `find`, `ls`, `cat`, `head`,
  `wc`, `grep`, read-only `git` commands and the metrics script only.
- Your only writes are under `reports/.artifacts/architecture-audit/`.
  Run first: `mkdir -p reports/.artifacts/architecture-audit/data`

## 1. Stack and workspace

Record, with the file that proves it:
- **Manifests**: `pubspec.yaml`, `package.json`, `pyproject.toml` /
  `setup.cfg` / `requirements*.txt`, `go.mod`, `build.gradle(.kts)`,
  `pom.xml`, `*.csproj`, `Cargo.toml`.
- **Workspace or monorepo tooling**: a `workspace:` list in the root
  `pubspec.yaml`, `melos.yaml`, `workspaces` in `package.json`,
  `pnpm-workspace.yaml`, `nx.json`, `turbo.json`, `lerna.json`, uv
  `[tool.uv.workspace]`, Gradle `settings.gradle` includes, a `.sln` with
  several projects.
- **The application**: which package or directory is the product being
  audited. In a monorepo with several apps, audit the one the user named;
  if none was named, audit the app whose entry point the most packages
  serve, and say so. A repository with no application in it is out of the
  standard's scope: say so in the artifact and stop.
- **The script language** for the metrics script: `dart`, `ts` (TypeScript
  or JavaScript), `py`, or `none` for any other stack.
- **Source roots**: the application's source directories and those of every
  in-repo package it depends on, directly or through another in-repo
  package (follow the path or workspace dependencies in each manifest); a
  workspace member outside that closure is out of scope (Dart: `lib` and `packages/*/lib`; TS:
  `src`, `apps/<app>/src`, `packages/*/src` or the package roots; Python:
  the package directories).

## 2. The metrics script

`graph-metrics-script.md`, in the same directory as this file, holds the
script between two marker lines. Extract it mechanically — never retype
or edit it:

```bash
python3 - "<path of graph-metrics-script.md>" reports/.artifacts/architecture-audit/data/graph_metrics.py <<'EOF'
import os, sys
if os.path.realpath(sys.argv[2]) != os.path.join(os.path.realpath('.'), os.path.normpath(sys.argv[2])):
    sys.exit(f'{sys.argv[2]} or a directory above it is a symlink; remove it and extract again')
text = open(sys.argv[1], encoding='utf-8').read()
body = text.split('<!-- graph_metrics.py:begin -->', 1)[1].split('<!-- graph_metrics.py:end -->', 1)[0]
code = body.split('```python\n', 1)[1].rsplit('\n```', 1)[0] + '\n'
open(sys.argv[2], 'w', encoding='utf-8', newline='\n').write(code)
EOF
```

The script checks its own digest on every run and stops with exit code 3
when its text differs from what was shipped. If that happens, extract it
again with the command above; if it still fails, stop and report it.

## 3. Inventory (`data/files.tsv`, `data/inventory.json`)

Run the script's inventory over the source roots:

```bash
python3 reports/.artifacts/architecture-audit/data/graph_metrics.py inventory \
  --root . --dir reports/.artifacts/architecture-audit/data --lang <lang> \
  --source <root> [--source <root> ...] [--exclude '<glob>' ...]
```

The script excludes tests, vendored and build directories and dot
directories (`.github/`, `.dart_tool/` and the like) itself, and marks
generated files as kind `gen`: they keep their edges but leave every size
metric. A file is generated by its name or directory (`*.g.dart`,
`generated/` and the like), as a Dart localisation output, or by its
header: the leading comment block (a Python module docstring included)
says the file is generated and also that it must not be edited, or
carries a standalone marker (`@generated`, "this file was generated").
For `--lang none`, pass `--ext` with the stack's source extensions.

Review `generatedByHeader` in `inventory.json`, the files only the header
rule marked, and the `gen` rows of `files.tsv` whose names you do not
recognise as generator output. Correct a wrong call with `--generated '<glob>'` or
`--handwritten '<glob>'` (repeatable, matched on the repo-relative path);
they win over every heuristic and keep the file's edges. Use `--exclude`
only for project-specific output that is not source at all, since it drops
the file and its edges. Record every override and exclusion with its
reason.

`inventory.json` also records the history facts the profile needs: whether
the clone is shallow, the repository's age, and the peak monthly
contributors over the last twelve months, counted over commits that touch
the source roots (`contributorPaths`), so other apps in a monorepo do not
count. Bot accounts are left out; `botsExcluded` lists them. Check that
list and the contributor count, and exclude a service account the rules
miss (a CI user without "bot" in its name) with `--bot '<glob>'`, matched
case-insensitively on the author name and email. Authors are counted by
name after `.mailmap`; when one person appears under several names and
the repository has no `.mailmap`, say so, and if merging them would change
the profile, record a profile override with that reason. A shallow clone
leaves the facts `null`; say so. Re-running the inventory with other
options rewrites `files.tsv` and `inventory.json`; check the module map
against the new `files.tsv` again.

## 4. Modules and roles (`data/module_map.tsv`)

Give each module one or more rows:
`<name>\t<role>\t<physical yes|no>\t<repo-relative path>\t<public surface>`.
Lines starting with `#` are comments. A module that spans several paths
gets one row per path, all with the same name, role, physical flag and
surface kind.

Identify modules in this order:

1. **Physical modules**: every workspace package, library, or project with
   its own manifest that the application uses.
2. **Feature modules** (standard section 1): one per user-facing capability.
   In a feature-first tree, the directories under its feature root
   (`features/`, `feature/`, `modules/`, or what the architecture
   documentation names). In a layer-first tree, one row per layer directory
   that holds the capability's code. A physical package that holds one
   capability's screens or endpoints is a feature too; one that holds only
   a single feature's data code is shared-domain (standard section 3). Do not make each screen a feature.
3. **Composition root**: the entry point, implementation selection, route
   or URL assembly, and composition widgets. Every root row has the name
   `root`, at file or directory precision; the script rejects a map with
   two root module names.
4. **Contract modules**: neutral contract modules and features' API modules
   (route keys, typed locations, path templates, interfaces, value types).
   Role `contract`. Check that each holds no screens, state or
   implementations; record one that does as an AP1 signal.
5. **Everything else** in the application: classify by what it holds and
   who depends on it, using the roles of standard section 3.

Roles, exactly as the script expects them: `root`, `contract`, `feature`,
`shared-common`, `shared-domain`, `global`, `foundation`.

Public surface column, always with repo-relative paths:
- `nonsrc`: a package whose internals sit under `src/` (Dart packages, many
  JS packages). Any file outside `src/` is public. The script rejects
  `nonsrc` on a logical module that has no `src/` directory, because it
  would make every file public; list the barrel files or use `-` there.
- A `;`-separated list of files: the barrel or index the module offers, for
  example `lib/features/cart/cart.dart` or `packages/ui/src/index.ts`.
  Every listed file must appear in `files.tsv`. A feature's surface is its
  barrel plus the route group it exports for the root (standard R4), when
  it has one.
- `-`: no public surface can be identified. Files other modules happen to
  import (a page the router imports) are not a surface unless a barrel, an
  index or the documentation names them. Edges into this module are
  unchecked; say so in the artifact. When more than half of the allowed
  cross-module edges are unchecked, R6 cannot be measured.

Rules for the map:
- Longest path wins: a file belongs to the row with the longest path that
  contains it, so a `root` row for `lib/app/router` and a `shared-domain`
  row for `lib/app` can coexist. A catch-all row (`.`) matches last.
- Every file in `files.tsv` must fall in some module. If a file fits no
  role, create a module for its directory and classify it; do not leave it
  unmapped.
- A directory that holds code of two roles is split into rows by
  subdirectory or file. Where it cannot be split, give it its
  most-depended-upon role and record it as **mixed** with the roles it
  holds. Shared code that you split out of the root's directories is
  recorded the same way: it is a C2 site (R5), counted once there, not a
  neutral relabelling.
- A barrel (a file that only re-exports) belongs to the module of the
  directory it indexes, whatever it re-exports. A module importing it
  depends on that module: a feature that imports the root's barrel to
  reach shared code is an R5 site, and the remedy is importing the shared
  module directly.
- Assign each file by what it holds before you look at the edges, and
  never move files afterwards to change a count. When a previous audit's
  `module_map.tsv` exists, start from it and record every row you change
  with the reason, so audits stay comparable.
- **Compact, layer-first codebases**: the profile is computed in step 2,
  so judge it here from `inventory.json` and the feature count: under
  20,000 handwritten lines, at most 8 features and at most 3 peak monthly
  contributors (or history unavailable). When
  such a codebase is organised by layer and capabilities cannot be told
  apart, map its product code as one feature module named `app` (one row
  per layer directory) and say so. Feature metrics are
  then not applicable for a Compact codebase; in a larger one, the missing
  separation is the finding.
- Classify from contents and dependents, not from the directory name
  alone. Cite one or two files per non-obvious classification.

## 5. Drivers and ownership (standard section 2)

For each driver, record whether it applies, the code it concerns, and the
evidence:
- **D1. Shared delivery**: several apps in the workspace using the same
  packages, a build that leaves out code another build includes
  (per-client or per-market builds), or documentation that another
  repository consumes the code. Per-environment entry points of one app
  (`main_development`, `main_staging`, `main_production`) and white-label
  builds that each ship the whole app do not count, and neither do
  showcase, example or gallery apps that no user receives.
- **D2. Several owning teams**: `CODEOWNERS` (or the equivalent) naming two
  or more teams, or documentation that says so.
- **D3. Deferred delivery**: Android dynamic-feature modules (the code
  must be a physical module), or Dart `deferred as` imports, Flutter
  `deferred-components` in `pubspec.yaml`, or JavaScript dynamic
  `import()` (the code must never also be imported eagerly). For the
  second kind, record each deferred library or chunk and whether any
  plain import of it exists (`grep` for its path).
- **D4. Published package**: a package meant for publication (a Dart
  package without `publish_to: none`, a `package.json` without
  `"private": true` and with a publish configuration).

Ownership: when `CODEOWNERS` or an equivalent exists, record which modules
have a declared owner (metric M11, scored only in the Large profile). With
no such file, M11 is 0 %, not unmeasured.

Profile override: if the operator stated a profile for this audit, record
it with the stated reason; otherwise record "none". Step 2 passes it to the
script.
